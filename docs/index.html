§0 Abstract

Which content pages should a client's SEO team review first for refresh? Using FlyRank's pseudonymized internship warehouse — 9.8 million daily search-performance rows across 44 clients, drawn from one mid-panel month (March 2026) — this paper builds a transparent CTR-and-volume rule baseline and tests three learned models (logistic regression, random forest, gradient boosting) against it under an honest, client-grouped validation split. The headline result is a negative one: none of the three models beat the hand-written baseline at any evaluated cutoff, and the strongest model's own held-out ROC-AUC (0.58) barely clears chance. The baseline rule — and a five-archetype action playbook built on top of it, not the underperforming model — powers the paper's ranked content-review recommendations. The output is decision-support: a triage queue a human reviews, never an automated verdict.

§1 Introduction

A content team managing a large site portfolio has more candidate pages for review than time to review them. In the slice studied here, an average client has hundreds of pages that could plausibly need attention this cycle — nobody opens all of them by hand. The practical decision is not "is this page declining" in the abstract; it's "of everything on my desk, what do I open first, and why?"

That's a ranking problem, not a classification problem, and it changes what "good" means. A model that separates classes well in aggregate is not automatically useful if its top-10 picks are wrong more often than a simple rule's top-10 picks — and that distinction is exactly what this paper tests.

The decision this supports: given a pool of existing content, rank pages by demand × risk of decline, attach a reason a human can check in one glance, and hand off a queue sized to real review capacity — not a flat, unranked list of everything that looks slightly off.

§2 Data

The dataset is the FlyRank/internship-warehouse release on Hugging Face — gated, pseudonymized production search data. Grain: one row = one (client, content item, day) — verified by grouping on the full key and confirming zero duplicates. Window: the month is split internally at day 15 — days 1–15 form the feature window, days 16–31 form the label window — giving a genuine past→future split inside a single month, rather than a same-window proxy.

Excluded, and why

  • GA4 engagement columns. Only 4.2% of March rows have ga4_data_available = TRUE; a raw GA4 feature would mostly encode "does this client have GA4 wired up," not real engagement.
  • Any raw name, domain, URL, or query. Not present in the release to begin with. Only pseudonym hash IDs (client_hash_id, content_hash_id) are used, strictly for grouping and joining — never as model features.
  • FlyRank's own product flags (health score, quick-win tags). Not shipped in this dataset by design — using a product's own decision flag as a model feature would be circular, teaching the model to reproduce an existing rule rather than find anything new.

§3 Methodology

Label

is_declining = imp_last < 0.8 × imp_prev, where imp_prev sums Search Console impressions over days 1–15 and imp_last sums them over days 16–31. This is a proxy for "losing search visibility," not a confirmed real-world outcome measured across months — but it is a genuine past→future split, which the starter dataset's own same-window trend label is not.

Features

Five features, all closed over the feature window only:

  • imp_prev, clk_prev — impressions and clicks, days 1–15
  • ctr_prev — clicks ÷ impressions, days 1–15
  • avg_position_prev — mean Search Console position, days 1–15
  • active_days_prev — days with any impressions, out of 15

imp_last is never a feature — it only builds the label.

Baseline

A transparent, hand-written rule: score = imp_prev × max(0, expected_ctr_for_position_tier − ctr_prev), applied only where imp_prev ≥ 100 and 0 < avg_position_prev ≤ 20. Before trusting it, two signals behind it were bucket-tested against the label:

Models

Logistic Regression and Random Forest, with Gradient Boosting tried as a stretch — the same five features, evaluated with precision@K rather than accuracy, because the real decision is "review the top K first," not "classify everyone correctly."

Validation design

GroupShuffleSplit on client_hash_id — grouped, not random by row. A random row split would let the model see other pages from the same client during training and partly memorize the client rather than learn the pattern.

Leakage checks

The feature/label timeline is drawn and enforced (feature window strictly precedes label window); the population filter (imp_prev > 0) uses only the feature window; no product flags appear anywhere. A direct confession test — add the exact future ratio the label is computed from, watch the score jump, remove it — was run on the final feature set:

Random Forest test ROC-AUC: 0.578 without the suspect feature → 1.000 with it added → back to 0.578 once removed. Exactly the pattern a genuine leak produces — confirming the final feature set is clean.

§4 Results

Test base rate: 0.366 (14,426 rows, 11 held-out clients). Random Forest's own held-out ROC-AUC: 0.578.

This is reported as the finding, not softened: added model complexity did not earn its keep here. Five basic features and 11 held-out clients weren't enough to out-rank a rule built on two already-confirmed signals. That is a legitimate, publishable result — a well-measured "no" is worth more than an inflated "yes."

§5 Limitations & Honest Framing

  • One mid-panel month. Every number here comes from March 2026 only — not checked against another month, a different season, or the sealed final month.
  • One proxy label. is_declining is a within-month impressions ratio, not a confirmed outcome measured across months.
  • 44 clients, one lane. Nothing here has been checked on other clients, verticals, or refresh-scoring approaches.
  • ~50% of rows have thin evidence (fewer than 15 of 15 active days in the feature window) — a real feature of a mixed-traffic portfolio, not a data defect, but it means roughly half the slice can't be scored with confidence by this method.
  • Decision-support only, never causal. "Review this page" is not "refreshing it will recover its traffic" — that claim needs a controlled experiment (a before/after refresh test), which this cross-sectional data cannot provide.
  • Retrospective, not a live forecast. The model and rule are fit and scored on the same March slice as a demonstration of the mechanics, not a claim about future months.

What a human must check before acting

  • Read the actual page — a flag says the math looks off, not why (branded/navigational query? a competitor's rich snippet? real content decay?).
  • Rule out consolidation, seasonality, and noise before treating a decline as real and page-specific.

What should never be automated

  • Never auto-publish a rewritten title or snippet — a candidate for human edit, not a diff to ship.
  • Never auto-prune, redirect, or delete a page from this queue — near-irreversible actions that need a content-strategy sign-off this data can't provide.
  • Never treat the model's probability or the rule's score as ground truth of cause — both rank candidates for review, and §4 already shows the model underperforms the rule here.
  • Never surface a real client name, URL, domain, or raw query in any downstream report.
